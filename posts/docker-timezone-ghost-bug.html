记一次由 Docker 时区引发的「幽灵 Bug」

2026-10-12/8 min read/#Docker#踩坑#Node.js

定时任务在本地跑得好好的，一进容器就迟到八小时。排查到最后，发现问题不在代码，而在 /etc/localtime。

现象#

需求很简单：每天上午九点给用户推一封日报。本地跑得稳稳的，部署到服务器之后，用户反馈邮件总是在下午五点才到——不多不少，正好晚了八个小时。

第一反应是服务器时间不对，登上去 date 一看，好家伙，显示的是 UTC。

bash
$ date
Mon Oct 12 09:00:00 UTC 2026

排查#

代码里用的是 new Date() 和 cron 表达式，逻辑上没有任何时区假设，问题只可能出在环境。挨个检查之后，定位到两个层面：

  • 宿主机本身是 UTC 时区，但之前的部署直接跑在宿主机上，代码里有段被遗忘的 TZ=Asia/Shanghai 兜底；
  • 这次改用 Docker 部署，容器是一个干净的 Ubuntu 镜像，/etc/localtime 不存在，环境变量也没有带 TZ。

容器里的 cron 按照 UTC 的九点触发，映射到东八区就是下午五点。代码没变，环境变了，Bug 就这么「幽灵」一样出现了。

根因#

容器不会继承宿主机的时区。对容器而言，世界默认从 UTC 开始。

想通这一点之后，修复方案就清晰了，二选一：

方案一：声明环境变量#

bash
docker run -e TZ=Asia/Shanghai my-app

或者在 compose 里统一声明：

yaml
services:
  app:
    image: my-app
    environment:
      TZ: Asia/Shanghai

方案二：挂载时区文件#

bash
docker run -v /etc/localtime:/etc/localtime:ro -v /etc/timezone:/etc/timezone:ro my-app

我最终选了方案一：环境变量声明更符合「配置显式化」的原则，不依赖宿主机的具体文件，换台机器也不会踩坑。

教训#

  1. 时间相关的问题，先怀疑环境，再怀疑代码。「我本地是好的」这句话，一半的功劳要记在环境一致上。
  2. 把 TZ 写进部署清单，和内存限制、重启策略放在一起，成为镜像交付的一部分。
  3. 更彻底的解法是内部一律用 UTC 存储与计算，只在展示层做时区转换——这是后话，本期日报服务先这样，记入 TODO。
